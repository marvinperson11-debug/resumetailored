# Phase 2 — inline editing

Built to your Q1 resolution: **site wins once touched.** On PR #271, all suites green.

---

## 1. The rule

```
edit   →  that field detaches from the resume; the site owns it now
reset  →  hand it back; follow the resume again
```

No pop-ups, no "which source?" question. Editing *is* the decision.

Without the detach, two things in your spec contradict each other — "the site updates automatically when you update your resume" and "click your name to change it" — and the contradiction resolves silently in the worst direction. Someone renames themselves, updates their resume a week later, and the site quietly discards the edit. They'd have no reason to look.

**The escape hatch:** a small `↺ Reset to my resume` chip appears under any field they've edited, only while editing. One click puts that single field back under the resume's control. If they never click it, their version stays forever.

---

## 2. What's editable

| | Behaviour |
|---|---|
| **Name** | Click → type. Enter saves, Escape cancels, clicking away saves. |
| **Headline / role** | Same. Derived as `role · location` from the resume. |
| **Summary** | Same, but **Shift+Enter** for a new line, Enter to save. |
| **Photo** | Click → file picker → replaced in place. |
| **Sections** | Click one → **↑ Move Up · ↓ Move Down · Delete** |

**Delete removes the section from the website only.** The resume store is never written to by anything in here — there's a test that asserts it against the real API after an edit.

A blank value is refused rather than saved: an empty heading looks like a broken page, not a choice.

---

## 3. Two decisions worth knowing

### Fields are found by meaning, not position

Each hero element carries `props.field` (`name`, `subtitle`, `summary`). Keying off *"the first heading in the first section"* would silently re-point at a different element the moment anything is reordered — so reordering would start overwriting the wrong thing. There's a test for exactly that case.

### The editor runs *inside* the iframe

That's where the real elements are. Reaching in from the parent with an absolutely-positioned overlay means re-deriving every element's box and keeping it aligned through scroll, resize and every re-render — which is where that approach usually breaks.

It never mutates the document. It posts each change out, and the parent applies it through the undo store. **One writer.**

## 4. Three things that came out of building it

**The undo store wasn't covering inline edits.** It was only created when the *advanced* editor opened, so everything done in simple mode bypassed it — directly against your item 6. The store is now created when the document loads, and the advanced editor *adopts* it rather than replacing it. That fixed a second bug too: opening the advanced editor used to discard the undo history of everything done in simple mode.

**Undo didn't redraw.** It updated the document without re-rendering the page, so nothing appeared to happen. The store's subscriber is now the single thing that triggers a render, so undo and redo repaint exactly like any other change.

**A regex in the generated edit layer collapsed to a literal newline** — which a regex literal can't contain. The edit layer is JavaScript generated by a template literal, so one stray backslash ships a syntax error that only appears in a browser console. There's now a test that parses every script the editable page emits.

## 8. Questions

Only two, and neither blocks anything.

### Q1 — Should `Delete` on a section ask first?

Right now it's immediate, undoable via the engine but with no visible undo yet (that's Phase 5). Deleting a whole section is the most destructive thing in the flow.

**My recommendation: leave it immediate and ship the fading undo next**, rather than adding a confirm dialog — a dialog on every delete is exactly the kind of interruption you've been cutting. But it does mean a mis-tap loses a section until Phase 5 lands.

### Q2 — What should happen on a page with no photo slot?

Three of the twelve templates have no image element in the hero. On those, "Add a photo" in the guided strip has nothing to fill.

Currently it does nothing visible, which is the worst option. **My recommendation: place the photo into the hero automatically** if there's no slot, rather than silently skipping. Small change; wanted to flag it rather than guess.
